GitHub Actions Runner Platform

Problem

GitHub-hosted runners were fast and convenient. The compute cost didn't scale with our usage.

So we moved to self-hosted. As our Paved Road scaled to more users, those runners started showing cracks:

  • Long queue times
  • Infrastructure instability
  • Runners were too lightweight, leading to slow dependency and artifact downloads, which led to even longer queue times
  • Not enough runners, too many runners, not enough runners, too many runners

The on-prem machines gave us good compute per cost. Network issues and intermittent outages meant we'd run out of runners entirely.

The users we had just onboarded onto the Paved Road were the ones hitting delays and outages, and the support channel let us know.

Those on call felt it at 2am EST.

My Role

This was a team effort. I focused on two core problems:

  • Runner startup was slow because every ephemeral runner redownloaded dependencies and artifacts.
  • Runner capacity swung between overprovisioned (wasted compute) and underprovisioned (long queue times).

I was new to Kubernetes and Terraform then, so I spent the first few weeks in Actions Runner Controller internals: why the existing architecture behaved the way it did, and where the scaling bottlenecks actually were.

What I Built

Slow runner startup

The answer was in the problem. Every runner started from a minimal base image, so each workflow reinstalled the same tools before any application code ran.

I built a custom runner image on top of our base that pre-installed the most-used tooling, close to what GitHub-hosted runners ship, without bloating the image. That moved installation work from every job execution to the image build, cutting startup time while keeping ephemeral runners ephemeral.

Then I updated our Helm charts so runner pods used the custom image alongside a Docker-in-Docker sidecar. Every new runner came up with its tooling already there.

Capacity that swung both ways

I led the migration from the original RunnerDeployment model to the RunnerScaleSet architecture in ARC v2. The newer model is conceptually simpler but scales on an entirely different mechanism, so the migration meant redesigning how runners were provisioned.

Instead of Kubernetes HPA guessing at capacity, ARC watched GitHub's job queue and provisioned ephemeral runners only when work existed. Idle runners went away, we scaled to zero when inactive and all the way up at peak, and queue times dropped.
